# Assumptions and Design Decisions

This document records assumptions and design decisions made for the Devices API. The implementation will follow the assignment requirements, with additional decisions documented where requirements are unspecified.

## 1. Device Identity

- Each device will have a server-generated UUID.
- Device IDs are unique and immutable.
- Device names and brands are not required to be unique.
- Multiple devices may have the same name and brand.

## 2. Device State

- Supported states are `AVAILABLE`, `IN_USE`, and `INACTIVE`.
- No additional state-transition restrictions are assumed beyond the assignment requirements.
- The initial state must be provided when creating a device.

## 3. Device Updates

- Device ID and creation time are immutable.
- Creation time is generated by the server in UTC.
- PUT replaces all mutable device properties: name, brand, and state.
- PATCH updates only the provided mutable properties.
- Name and brand cannot be changed while a device is `IN_USE`.
- Update restrictions are evaluated against the device's state before the operation.
- Attempts to modify immutable properties will be rejected.

## 4. Device Deletion

- Hard deletion is selected because audit history, recovery, and data retention are not required by the assignment.
- Devices in the `IN_USE` state cannot be deleted.
- Deleting a device permanently removes its database record.

## 5. Data Validation

- Name and brand are required and cannot be blank.
- Name and brand have a maximum length of 255 characters.
- Device state must be one of the supported values.
- PostgreSQL constraints will enforce primary key uniqueness, required fields, and valid states.
- Name and brand will not have unique constraints.

## 6. Concurrency

- JPA optimistic locking using `@Version` is planned to detect conflicting concurrent database transactions.
- Update and delete operations will use transactional boundaries.
- Concurrency conflicts will be handled explicitly.
- HTTP conditional requests using ETag or If-Match are outside the initial scope.

## 7. Security

- HTTP Basic authentication will be used to protect the API.
- Authentication credentials will be configurable through environment variables.
- No credentials will be stored in source control.
- HTTPS will be required for secure production deployment.

## 8. Data Initialization

- Production will start without predefined device records.
- Development-only sample data may be provided for testing and demonstration.
- Integration tests will manage their own isolated test data.

## 9. Future Improvements

The following features are outside the initial scope but may be considered if requirements evolve:

- Audit logging and device change history.
- Soft deletion and retention policies.
- Advanced authentication and role-based authorization.
- HTTP conditional requests to prevent stale client updates.
- Additional monitoring and operational improvements.
